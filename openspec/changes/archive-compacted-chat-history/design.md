## Context

聊天压缩已能生成受来源 ID 约束的摘要，但原消息继续留在 `chat_messages`，而聊天流在准备、持久化 user 消息和结束刷新时重复读取完整会话。现有摘要边界可准确标识应从热路径移出的前缀。

## Goals / Non-Goals

**Goals:**

- 将已覆盖消息迁入独立归档表，保留原始内容和元数据
- 聊天运行时只查询活跃消息，压缩后重置热表边界
- 读取、清除和删除会话保持完整历史语义

**Non-Goals:**

- 不设置物理删除保留期；在没有审计与合规要求前不删除可追溯历史
- 不新增前端的历史分页界面

## Decisions

- 归档表复用消息字段并记录 `archived_at`，而不是把正文塞入摘要 JSON；这保持引用、工具元数据和消息 ID 可查询
- 在摘要状态与归档迁移的同一 SQLite 事务中完成迁移并把 `compacted_message_count` 重置为零，避免摘要覆盖范围与热数据不一致
- 添加活跃消息查询供 Agent 使用；完整历史查询合并归档与热表，维持已有 API 的读取语义

## Risks / Trade-offs

- [完整历史 API 仍可能返回大量记录] → 运行时热点已分离；前端分页接口在真实 UI 容量需求出现时单独实现
- [历史归档保留会继续占用冷存储] → 这是保留证据的安全默认值；后续由具备审计策略的清理任务处理

## Migration Plan

1. 新增归档表和 owner/session/时间索引，存量热消息不迁移
2. 后续每次成功压缩时迁移本次覆盖前缀
3. 回滚时保留归档表，旧版本仍可运行但不会读取归档内容；因此需在回滚前停止新压缩任务
