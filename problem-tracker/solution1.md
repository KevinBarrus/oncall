# 第一轮解决方案与实施记录

本文件中的方案编号与 `problem1.md` 中的问题编号一一对应。已完成项记录实际实现；未完成项保留为后续方案，不代表已经上线。

## 问题1的解决方案：为记忆压缩增加独立输入预算

- 使用独立的摘要输入预算，按旧消息边界分批选择，避免一次性提交全部历史。
- 单条超长消息进行有界首尾保留，近期消息继续保留在 Agent 上下文中。
- 已完成实现并补充记忆压缩边界测试。

## 问题2的解决方案：增加 Agent 运行时预算跟踪

- 区分历史输入预算、工具调用预算、输出预留和安全余量。
- 运行期间累计工具参数、工具结果、错误结果和模型流式输出。
- 超预算时停止继续执行并通过 SSE 返回上下文超限错误。
- 当前使用 LangChain 近似 token 统计，真实模型 tokenizer 作为后续增强。
- 已完成实现并补充运行时预算测试。

## 问题3的解决方案：将自由文本摘要升级为结构化记忆

- 使用带版本的 JSON 记忆，按目标、事实、决策、待办、来源和最近上下文分类。
- 每条记忆保存来源消息 ID；校验失败时不覆盖旧摘要，并兼容读取旧版摘要。
- 已完成实现并补充来源 ID 校验测试。

## 问题4的解决方案：为工具输出增加可追溯的结构化压缩结果

- JSON 工具结果保留机器可读字段，不再先转换为自由文本。
- 压缩 envelope 增加 `mode`、`sourceHash`、`originalChars`、`compressedChars` 等元数据。
- SearchLog 保留结构化字段、聚类信息和解析失败时的原始预览。
- 已完成实现并补充工具结果和 SearchLog 测试。

## 问题5的解决方案：增加会话级并发保护

- 在 `ChatStreamingService` 的流式入口按 `owner_user_id + session_id` 获取共享异步锁。
- 锁覆盖记忆准备、用户消息追加、Agent 执行、助手消息持久化和用量刷新，确保同一会话的完整请求串行执行。
- 使用进程内弱引用锁表，避免 API 每个请求新建 `ChatStreamingService` 时锁失效。
- 已补充两个独立 Service 实例并发访问同一会话的测试。
- 多进程部署时仍需升级为数据库版本号/CAS，确保跨进程的摘要边界和消息追加原子一致。

## 问题6的解决方案：增加真实聊天链路端到端评测

- 通过真实 HTTP API 创建会话并调用 `/chat/sessions/{id}/messages:stream`。
- 解析真实 SSE，统计回答、引用、工具调用、完成事件和端到端延迟。
- 使用真实链路返回的引用参与 Judge 评测，并将结果独立写入 `endToEnd`。
- 已完成实现，使用 `--e2e` 显式执行，避免普通离线评测额外消耗模型调用。

## 问题7的解决方案：扩充分层评测集

- 按文档规模、文档类型、查询类型、语言、版本变化、权限隔离和空知识库建立分层数据集。
- 每层单独统计结果，并报告重复运行的均值、方差或置信区间。
- 当前 fixture 已从 15 道题扩充到 24 道题，覆盖团队规范、服务拓扑、历史故障和知识库无答案问题。
- 数据准备脚本已上传与题目匹配的 3 篇团队文档，并保留 3 篇无关运维文档作为噪声文档。
- 评测结果增加 answerable/unanswerable 与参考文档的分层分布，避免只看总平均分。
- 当前仍属于小规模 fixture，10/100/1000 篇文档规模、更多文档类型和置信区间属于后续扩展，不据此下系统级结论。
- 已补充数据集规模和分层分布测试。

## 问题8的解决方案：使用人工相关性和原子事实标注

- QA 的 `reference` 和 `atomic_facts` 共同形成 chunk 级人工相关性：覆盖原子事实记为 2 分、同源但未覆盖记为 1 分、其余记为 0 分；MRR 和 NDCG 不再由答案 token overlap 自动打标。
- 每道 QA 增加 `atomic_facts`，以人工拆分的原子事实计算 `Atomic Fact R@5`。
- token overlap 保留给错误分类等辅助诊断，不再决定确定性检索指标。
- 已补充人工来源相关性和原子事实召回测试。

## 问题9的解决方案：区分 Judge 分数和 Judge 失败

- Judge 返回结构化结果：成功时返回 `score`，失败或格式错误时返回 `score: null` 与错误类别。
- 只接受完整的 0 到 1 数值，拒绝从任意文本中提取第一个数字。
- 汇总时排除无分数样本，并在每道题记录 `judgeErrors`，在策略汇总中记录 `judge_failure_count` 与 `judge_failure_rate`。
- Judge 不可用时不再执行误导性的错误分类，而是标记为 `judge-unavailable`。
- 已补充 Judge 超时和格式错误测试。

## 问题10的解决方案：拆分真实文档 baseline 与 answer-injection 检查

- 使用 QA 的人工来源标签读取原始团队文档，作为 `goldDocumentBaseline`，衡量生成模型面对真实文档上下文时的表现。
- 标准答案直接注入上下文的结果独立命名为 `answerInjectionSanityCheck`，仅检查生成和 Judge 流程，不再称作生成上界。
- 报告表格展示 gold-document baseline，并单独输出 answer-injection 检查结果。
- 已补充测试，确保 gold-document baseline 不读取标准答案作为上下文。

- 增加唯一作用域、审计、备份和并发更新语义，删除用户目录 JSON。
- 当前待实现。

## 问题12的解决方案：只对实际使用的 SOP 归因

- 检索结果只记录曝光，不直接更新成功率。
- 只有 SOP 被计划引用、被执行或在诊断报告中明确作为依据时，才写入结果证据。
- 记录证据强度和归因阶段，避免把候选 SOP 的曝光当成成功原因。
- 当前待实现。
