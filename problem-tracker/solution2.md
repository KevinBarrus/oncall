## 问题1的解决方案：使用真实 tokenizer 计数

- 优先调用当前聊天模型暴露的 token 计数能力；远程模型未暴露 tokenizer 时使用保守 Unicode 回退，而非按字符数除四。
- 已完成：聊天历史、摘要输入、运行时预算和工具输出压缩阈值复用同一入口。回退值取 LangChain 近似值与非空白 Unicode 字符数的较大者，避免低估中文和混合日志。
- 已补充模型优先、中文回退、运行时预算和工具压缩阈值测试。

## 问题2的解决方案：让工具证据可按需取回

- 将原始工具输出持久化为受 owner/session/task 作用域保护的证据，压缩结果保存可回查 ID、哈希和范围。
- 为日志、JSON 和指标分别采用结构化无损字段保留；Agent 需要细节时通过受控工具展开原文或指定片段。
- 已完成：压缩原文保存至 owner/session 作用域 SQLite 证据表，压缩结果附带 `evidenceId`，Agent 可通过当前会话的 `read_tool_output_evidence` 工具按需展开

## 问题3的解决方案：为压缩提供降级与非阻塞体验

- 摘要格式或模型调用失败时保留旧记忆、记录可观测事件，并继续使用预算内原始历史。
- 将主动压缩移入现有持久任务运行时；请求路径只在必须释放预算时执行一次有超时的压缩。
- 已完成：30 轮和 70% 阈值仅投递 owner 范围的 `chat_memory_compaction` 持久任务，当前聊天继续使用原始历史；达到 95% 硬限时才同步压缩一个批次，超时或失败保留原状态并按既有上限语义处理

## 问题4的解决方案：限制手动压缩工作量

- 手动模式只提交一次受摘要输入预算约束的旧消息批次，而不在请求内循环压缩全部历史。
- 全量归档式压缩改为后台任务，并向前端返回任务状态。
- 已完成：切换到 `manual` 或显式压缩只投递一个 `chat_memory_compaction` 持久任务；任务执行仍复用单批次 `compact_once()`。
- 已完成：两个接口返回会话和 owner 范围的后台任务，前端可用既有后台任务查询接口跟踪状态。
- 已补充：手动模式不再同步调用摘要模型、任务返回及跨 owner 查询隔离的回归测试。

## 问题5的解决方案：持久化跨轮工具证据索引

- 将工具调用、结构化结果、引用和压缩指针作为会话证据保存，而非只保留 assistant 文本。
- 下一轮仅注入与当前问题相关的证据摘要；需要原文时由证据展开工具按权限读取。
- 已完成：后续聊天请求注入本 owner 与本会话最近完成的工具审计摘要和历史 citation，保留压缩结果中的 `evidenceId`；最多 6 条审计、8 个 citation、4,000 字符，原文仍通过现有受控工具按需读取

## 问题15的解决方案：校验摘要忠实性

- 保留现有结构和来源 ID 校验，并对数字、错误码、决策和待办进行规则化一致性检查。
- 高风险摘要使用原文片段复核或低频 Judge 抽检；校验失败不覆盖上一版记忆。
- 已完成：结构校验通过后执行忠实性校验，摘要与条目数字必须可追溯到原文，decision/todo 条目需与原文共享字面证据。
- 已完成：校验失败抛出 `MemoryFidelityError`，保留上一版记忆并保持压缩边界不变。
- 已完成：补充数字编造、决策无依据、忠实摘要通过和失败不覆盖的回归测试。
- 限制：不做 LLM-as-judge 或低频抽检复核；语义级忠实性留待明确需求后评估。

## 问题16的解决方案：复用 MCP 连接和发现结果

- 在应用生命周期维护按用户/连接配置分区的 MCP 客户端与短 TTL 工具发现缓存。
- 对连接池设置上限、失效、超时和显式关闭语义，避免将每次调用都变成握手。
- 已完成：应用进程按用户启用连接配置复用客户端；配置变化时关闭并替换旧客户端，应用关闭时释放全部客户端。
- 已完成：每个 MCP Server 复用一条串行会话并缓存 60 秒成功发现结果；调用异常时丢弃会话并沿用既有重试重连。
- 已完成：LangChain MCP 工具统一通过 ToolRegistry 执行器调用，不再由 adapter 绕过会话复用层。

## 问题17的解决方案：隔离故障 MCP 连接

- 工具发现按连接分别捕获失败；健康连接继续注册，失败连接记录不可用原因。
- 仅当用户请求的工具所属连接不可用时返回对应错误，并在 readiness 输出逐连接状态。
- 已完成：`LocalMcpClient` 逐连接发现工具，失败连接不会阻断健康连接工具注册；全部失败时返回空 MCP 工具集，不伪造工具或证据。
- 已完成：MCP readiness 同时返回聚合结果和每个连接的名称、endpoint、工具数、状态及安全错误；应用在首次实际使用 MCP 时才创建运行时服务，使无效配置仍可由 `/config/check` 报告。
- 已补充：健康与故障连接共存、全部发现失败和 readiness API 逐连接状态的回归测试。

## 问题25的解决方案：缓存 LLM 探活结果

- 对同一 provider/model 的 readiness 结果设置短 TTL；TTL 内 `/ready` 直接返回缓存。
- 配置变更或缓存过期后才发起真实 LLM 请求，并报告缓存状态与最后检查时间。
- 已完成：Provider 在单进程内缓存成功或失败的安全 readiness 结果 30 秒，`/ready` 与 `/config/check` 会复用该结果而不重复调用模型。
- 已完成：缓存未命中时使用双重检查与异步锁合并并发探测，过期后自动重新调用模型。
- 已补充：缓存命中、过期重探测与并发单飞回归测试。

## 问题26的解决方案：避免每次重建全量 BM25

- 先以知识库版本为键缓存 BM25 索引；文档索引完成、删除或版本变化时失效重建。
- 知识库达到阈值后改用支持倒排索引的检索后端，避免 Milvus `limit=-1` 全量扫描。
- 已完成：按 owner 与排序后的知识库集合缓存 BM25 chunk 语料和 scorer 60 秒；无过滤查询复用缓存，避免重复全量读取与构建。
- 已完成：文档或元数据过滤仍在缓存 chunk 上重新过滤与评分，保证不会返回范围外内容。
- 限制：当前没有知识库版本或索引完成通知，因此缓存以 TTL 失效；后续补齐版本信号后应改为版本化即时失效。
- 已补充：缓存命中和知识库作用域隔离回归测试。
